# Supabase implementation review and patch plan

Reviewed October 7, 2026. Baseline: `88de3d046b0568edb4ddce55d5912a5e3643e7cf`
(`feat: add experimental Supabase lifecycle and uv workflow`), compared with
parent `f06d79e`. The implementation was committed before this review. This
document requests follow-up patches; it does not implement them.

The review found three reproducible SQL/runtime defects, plus documentation
inconsistencies. The previously recorded real Edge proxy disconnect failure
also remains an acceptance gate. Passing contract tests do not close these gaps.

## R1 — P1: valid claim batches can terminate the worker

Locations at the baseline:

- `supabase/experiments/relay-spike/queue.sql:390–405`
- `oshepherd/backends/supabase/client.py:107`
- `oshepherd/backends/supabase/worker.py:127–136,307–308`

`heartbeat_and_claim` limits the number of jobs but not the encoded size of its
response. It changes each selected job to `running` and returns every full
request. Each request may approach 1 MiB and a worker may have 64 slots. The
Python RPC reader rejects responses larger than 2 MiB. That exception escapes
the worker control loop, terminating the worker and cancelling its other local
tasks, while SQL retains the newly assigned jobs until lease recovery.

**Reproduced through local Auth/PostgREST:** create one disposable enrolled
worker, set its fixture-scoped capacity to 3, and submit three async non-streamed
`generate` requests for `test:latest`, each with an 800,000-character ASCII
prompt. All three submissions succeed. `heartbeat_and_claim(max_jobs=3)` raises
`RpcError("response_too_large")`. A scoped SQL count then reports **3 running
jobs**. No inference needs to run. These inputs are within the documented
request, caller admission and worker capacity limits.

Patch:

1. Define a shared maximum encoded claim-response size, accounting for the full
   RPC envelope, stop list and job metadata. Document it in the protocol.
2. Select a bounded set that fits before committing assignments. Leave remaining
   jobs queued. Preserve model routing, capacity accounting, deterministic
   operation replay and attempt fencing. Ensure any valid single request can
   make progress; do not silently lower the advertised per-request limit.
3. Keep finite client response limits. Raising the cap to accommodate 64 maximum
   requests alone would undermine the bounded worker control path.
4. Add real SQL and worker-loop regression coverage. Include three large jobs,
   mixed sizes, near-boundary JSON escaping/Unicode, active-attempt stop entries,
   and an identical operation replay after a lost acknowledgement. Assert the
   worker survives, only returned jobs are assigned, and later claims make
   progress without duplicate attempts.

## R2 — P2: prompt copies survive content cleanup in claim receipts

Locations at the baseline:

- `supabase/experiments/relay-spike/queue.sql:399–405,648–665`
- `docs/plans/supabase/implementation.md`, “Size and retention policy”

Claim operation receipts store the entire response, including every prompt.
Their `job_id` is NULL. Content cleanup clears `jobs.request`, chunks and results
but cannot associate these receipts with the purged job. Age-based receipt
cleanup retains them for two days, independently of the 30-minute synchronous
content retention and one-day async retention. Backlogs can extend this further.
The receipt window should preserve replay identity, not unnecessary raw prompt
copies after terminal content cleanup. This concerns active database retention;
it is not a claim that unauthorized workers can read those rows.

**Reproduced through local Auth/PostgREST:** submit and claim one synchronous
job whose fixture prompt is `hello`; cancel it with its consumer token. Set only
that generated cluster's job `content_expires_at` to one second in the past and
invoke `purge_expired(limit=32)`. The RPC reports **1 purged job**. Scoped SQL
reports both **job payload cleared = true** and **claim receipt retains prompt
= true**, using `response #>> '{data,jobs,0,request,payload,prompt}'`. No prompt or
credential was printed by the reproduction.

Patch:

1. Prefer claim receipts containing immutable assignment/replay metadata without
   duplicate request payloads. Reconstruct a replay only from still-authorized,
   live attempts and their retained requests, preserving the existing response
   identity and stale-attempt behavior.
2. Alternatively, introduce explicit receipt-to-job references and bounded
   redaction when each job's content expires. A multi-job receipt must not keep
   one expired job's payload solely because another job is active.
3. Handle existing experimental receipts when applying the patch. Do not assume
   fresh installations or discard all operation identities to erase content.
4. Add sync and async retention tests that inspect all payload-bearing tables,
   not only `jobs`/`chunks`. Cover mixed-job receipts, multiple cleanup passes,
   active jobs, terminal replay and tombstone expiry. Confirm content is removed
   while hashes/identifiers still prevent duplicate operations or inference.

## R3 — P2: the original queue deadline prevents lease recovery

Locations at the baseline:

- `supabase/experiments/relay-spike/queue.sql:191–203,219–224`
- `protocol/supabase/v1/README.md`, “Output, state and async API”

`retry_or_fail` requires the original queue deadline to remain in the future,
even for a job that already left the queue and ran. A default synchronous queue
budget is 30 seconds, shorter than the 45-second worker lease. Consequently, a
worker that disappears just after claiming a synchronous job cannot recover by
lease expiry under these defaults: it fails on its first attempt despite no
published output, a live consumer, and remaining execution time. Async jobs
encounter the same restriction after their original 60-second queue deadline.
This conflicts with the documented recovery policy based on output, attempt
count and total execution deadline.

**Reproduced with fixture-scoped timestamp advancement:** submit and claim a
default synchronous non-streamed job, then set its queue deadline 15 seconds in
the past and its worker lease one second in the past, leaving its execution
deadline and consumer lease untouched. Run `reap_jobs(limit=32)`. Observed:
`state=failed`, `attempts=1`, `output_bytes=0`, `total_budget_remaining=true`,
`consumer_alive=true`, `error_code=worker_lost`. This reproduces the relevant
deadline ordering without sleeping for a full lease.

Patch:

1. Make initial queue admission and retry waiting semantics explicit. Recommended:
   retain the original execution deadline, grant an eligible retry a bounded new
   queue wait, and cap it by the remaining execution budget. Persist the necessary
   queue-budget value rather than accidentally reusing an elapsed timestamp.
2. Update retry transition, claim eligibility and reaper behavior together.
   Removing only the predicate in `retry_or_fail` would leave the requeued job
   immediately expirable and ineligible for claim.
3. Preserve consumer cancellation, revoked/stale attempt fencing, backoff,
   capacity release, attempt ceiling and the prohibition on inference retry
   after any durable output. Never extend the total execution deadline.
4. Add real SQL recovery tests with queue deadline < expired worker lease < total
   deadline, for sync and async jobs. Verify a second authorized worker can claim
   the retry, the old attempt cannot mutate it, initially unclaimed overdue jobs
   still expire, and output/consumer/total-deadline exclusions remain terminal.

If an absolute submission-relative retry cutoff is actually desired, document
that product decision and its lack of default synchronous worker-loss recovery
explicitly; do not continue advertising the broader recovery behavior.

## R4 — P3: current instructions do not consistently describe the uv workflow

Locations at the baseline:

- `scripts/supabase_demo.py:3,433` recommends bare `python -m ...` in its module
  instructions and setup success message.
- `docs/plans/supabase/progress.md:150` does the same in current usage guidance.
- `README.md:298–302` asks users who started only Redis/API/worker/Ollama to run
  all of `tests/`, which now includes separately provisioned Supabase integration
  tests and the known strict Edge failure.
- `docs/plans/supabase/index.md` still describes 162 passing tests and the initial
  characterization/spike as the next step despite the implemented local lifecycle.

Patch current guidance and emitted shell commands to use `uv run --locked`.
Separate the service-free, Redis, local Supabase and opt-in real-model test
recipes with their actual prerequisites. Keep the strict Edge gate visible.
Point the overview at the authoritative ledger or update its status. Retain
historical verification commands as historical evidence, and keep runtime
`sys.executable` child processes inheriting the uv-managed interpreter.

## Existing gate — real Edge proxy disconnect

This was known before the review and is recorded in the
[progress ledger](progress.md). Local Edge Runtime 1.74.3 did not propagate the
reader disconnect into SQL cancellation; the job succeeded. The strict test is
`test_real_edge_first_record_before_terminal_and_disconnect` in
`tests/integration/supabase/test_edge.py`. Deno handler cancellation tests and
the FastAPI socket-disconnect test do not establish proxy behavior. This review
reran the strict test and again observed `succeeded` instead of `cancelled`.

Investigate runtime/proxy abort propagation and any supported response lifecycle
hook with that real test. Validate that closing the HTTP reader cancels the SQL
job and upstream execution within a declared bound. If this runtime cannot
provide the signal, document the limitation and establish a supported deployment
or protocol decision before claiming the gate is closed. Do not weaken the
assertion, mark it passed, replace it with a FastAPI-only result, or fabricate a
terminal inference record. No hosted deployment is authorized by this review.

## Additional investigation — intermittent Edge 503

The broad local integration run failed
`test_real_edge_large_success_requires_authorized_download` at its initial
submission: expected 202, received 503 (`test_edge.py:143`). A focused rerun of
that same test passed. The cause is not established, so this is an unresolved
test observation rather than a fourth confirmed runtime defect. Investigate
function readiness/restarts, the response's safe error code, SQL admission and
protected runtime diagnostics if it recurs. Keep diagnostics redacted. Do not
hide it by adding blind inference retries or claiming the broad run was green.

## Patch order and constraints

1. Add regression coverage for R1–R3 and preserve the failing baseline evidence.
2. Implement R1 and R2 together if the claim receipt representation changes;
   otherwise use separate focused commits with replay tests at each boundary.
3. Implement R3 with the documented queue/retry semantics and recovery tests.
4. Correct R4 and update protocol/ledger claims to match verified behavior.
5. Investigate the existing Edge disconnect gate separately; report it as open
   until the actual proxy regression passes.

Keep Redis the default and keep experimental SQL under
`supabase/experiments/relay-spike/`. This patch package is not the installer,
production migrations, or hosted/load qualification. Preserve unrelated local
files, including `docs/plans/github-pages-publication.md`. Use uv for Python
commands and keep Conda optional. Never include private connection files,
credentials, raw prompts or result content in test output or commits.

Reproductions used `queue_harness` and `scoped_sql` from
`tests/integration/supabase/harness.py` against the existing isolated local
API at port 55321 and PostgreSQL at port 55322. Fixture capacity/timestamp edits
were limited by generated cluster UUID. Every fixture cluster and Auth identity
was removed in the harness cleanup. They did not touch the persistent demo,
run Ollama inference or download models.

```sh

deno test --allow-read=protocol supabase/functions/ollama/gateway_test.ts
```

  deprecation warning, 11.61 seconds.
